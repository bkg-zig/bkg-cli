# Deploying OneCLI to Railway

Railway does **not** run `docker/docker-compose.yml` as a Compose stack: it
cannot create Compose services, profiles, networks, volumes and startup
ordering from that file. Instead, every long-running container becomes a
Railway _service_ in one project, connected by Railway's private network.

The self-host path in [`docs/self-hosting.md`](self-hosting.md) remains the
full-stack option (`docker compose up -d --wait` on a Docker host you
control). Railway cannot supply the host Docker socket or the internal fenced
sandbox network, so the Docker-backed services (`runner`, `ssh-terminator`)
stay on a Docker host.

## Topology

The topology lives in [`.railway/railway.ts`](../.railway/railway.ts) and is
applied with the Railway CLI:

```sh
railway link --project <project-id> --environment production
railway config plan      # preview
railway config apply     # apply
```

| Compose service  | Railway service | Image            | Port  | Notes                                                        |
| ---------------- | --------------- | ---------------- | ----- | ------------------------------------------------------------ |
| `postgres`       | `Postgres`      | managed database | 5432  | `DATABASE_URL` is referenced as `${{Postgres.DATABASE_URL}}` |
| `migrations`     | `migrations`    | Dockerfile       | —     | one-off job, `restartPolicyType: NEVER`                      |
| `api`            | `api`           | Dockerfile       | 10256 | health `/v1/health`                                          |
| `web`            | `bkg-one-cli`   | Dockerfile       | 10254 | health `/healthz`                                            |
| `gateway`        | `gateway`       | Dockerfile       | 10255 | health `/healthz`, volume `/app/data` (the CA)               |
| `runner`         | —               | Dockerfile       | —     | needs `/var/run/docker.sock` — not on Railway                |
| `ssh-terminator` | —               | Dockerfile       | —     | needs the Docker socket and raw SSH — not on Railway         |

The Dockerfiles (`docker/api.Dockerfile`, `docker/web.Dockerfile`,
`docker/gateway.Dockerfile`, `docker/migrations.Dockerfile`) need the full
repository as build context, so the services keep the repository root as their
root directory.

## Deploying

```sh
scripts/deploy-railway.sh
```

The script is the operator entry point. It

1. refuses to run on a branch other than `tango` and pushes it (Railway
   builds the pushed commit),
2. applies `.railway/railway.ts` (plan first, so a destructive change stops
   the run),
3. creates/points the public domains at the ports the images listen on,
4. writes the runtime variables,
5. deploys **migrations first** and waits for them to succeed before api,
   web and gateway start against that schema,
6. checks the public health endpoints.

Useful flags: `--dry-run` (change nothing), `--skip-push`, `--skip-iac`,
`--project=ID`, `--confirm-destructive`.

## Variables

The three secrets below exist as **shared variables** of the Railway project
and are referenced by the services (`${{shared.NAME}}`). They are never
generated by the deploy script: a fresh `SECRET_ENCRYPTION_KEY` would orphan
every encrypted credential in the database.

- `SECRET_ENCRYPTION_KEY` — web, api, gateway.
- `GATEWAY_INTERNAL_SECRET` — api, gateway.
- `BETTER_AUTH_SECRET` — web, api.

The deploy script sets the non-secret wiring:

- `DATABASE_URL` — `${{Postgres.DATABASE_URL}}` on migrations, api, web and
  gateway.
- `ONECLI_EXTERNAL_URL` / `APP_URL` — the public dashboard URL.
- `API_URL` — the public API origin; `GATEWAY_API_URL` — the public gateway
  origin.
- `ONECLI_TRUSTED_ORIGINS` — the dashboard origin (CORS allow-list).
- `PORT` — the port the image listens on (10254 web, 10256 api, 10255
  gateway). Railway's default is 8080; the OneCLI images listen on their own
  ports, so the value must match the domain's target port.
- `ONECLI_BIND_HOST=0.0.0.0`, `ONECLI_APP_PORT`, `ONECLI_API_PORT`,
  `ONECLI_GATEWAY_PORT`, `GATEWAY_INTERNAL_URL`, `API_INTERNAL_URL`,
  `INTERNAL_API_URL`, `ONECLI_AGENT_PROXY_ADDRESS`.

`BETTER_AUTH_COOKIE_DOMAIN` stays **unset** on Railway: the public domains
are siblings under `up.railway.app`, and a cookie scoped to that shared
parent would be readable by every other application on it. Without it
Better-Auth issues a host-only cookie, which the dashboard sends to the API
because both are same-site.

## Limitations

- The Docker-backed runner (`runner`, `ssh-terminator`) and the agent sandbox
  network do not exist on Railway. Run them on a Docker host, or use the
  Kubernetes installation described in the self-hosting guide.
- The gateway keeps its CA in the `/app/data` volume. Deleting the volume
  invalidates every certificate the gateway has issued.
